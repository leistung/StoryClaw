# 11 部署运维与上线准备

## 当前部署是什么

当前`deploy/docker-compose.yml`是开发编排：两个前端使用Vite，API和Worker支持代码热更新，部分基础设施发布宿主机端口。不能直接将这份配置视作已经通过生产验收。

两个前端目录适合独立发布，并不要求两台机器。Docker安装在Linux服务器上运行各服务；前期可以采用单机Compose，但同机共享资源与故障域，不是高可用。具体规格应由实际并发、索引量和压测决定，本手册不作用户容量承诺。

建议的生产流量关系：作者端域名/中台域名 → HTTPS网关 → 静态前端与API；Worker和数据库走内部网络。前端构建结果可由Nginx或独立静态托管提供。

## 当前日常命令

```bash
make up-all
make health
make logs
make down
```

所有命令在根目录使用`.env`和`deploy/docker-compose.yml`。Compose项目名固定为storyclaw，根目录迁移不需要改项目名或删数据卷。前端与后端端口见[02](02-本地运行与配置.md)。

## 正式上线前的工程工作

| 领域 | 当前情况 / 必须补齐 |
| --- | --- |
| 镜像与发布 | 改为固定版本镜像，两个前端产出静态文件，关闭reload和源码挂载；支持回滚 |
| 网关 | 正式域名、HTTPS、上传限制、流式响应超时与缓冲设置 |
| 网络 | 仅发布必要入口；数据库、etcd、Milvus和MinIO不直接暴露公网 |
| 密钥 | 替换开发占位值，管理访问凭据、备份与轮换流程；JWT密钥还参与现有API密钥加密派生，不能无计划直接轮换 |
| 数据库 | 建立并验证迁移基线，在测试副本演练升级和回滚；开发create_all不能升级所有已有表结构 |
| 可靠性 | 真实依赖就绪检查、Worker失效告警、任务租约恢复演练、供应商故障观察 |
| 数据保护 | SQL/原稿/知识存储的异机备份、恢复演练、存储增长与保留策略 |
| 商业流程 | 在线支付、回调幂等、退款、对账与用户权益；内容运营和用户数据管理流程 |

这是上线准备清单，不表示这些项目全部已实现。具体经营、备案和内容义务应按实际部署地域及业务形式另行确认，不从技术方案直接推导资质结论。

## 数据迁移与备份

当前开发启动有`Base.metadata.create_all`，迁移文件另在`backend/alembic`。`make migrate`执行Alembic head，但已有开发库必须先核对迁移历史，不能盲目运行或随意stamp掩盖差异。

业务备份至少覆盖PostgreSQL、MinIO中的私有原稿，以及知识库恢复所需数据。仅备份代码或容器镜像不够；同一块云盘上的另一个目录也不等于异机备份。备份应在隔离环境验证可恢复。

## 运行中排错

先看活动任务、服务健康和日志，再看数据库/存储与模型配置。不要遇到错误就清库、prune或删除失败回执。结果未知的付费请求不能简单自动重发；按[08](08-任务确认与积分计量.md)核对候选与用量。

中台操作依赖后端管理员权限；独立域名不是权限隔离。生产环境还应评估中台访问限制、审计留存与最小权限。

部署文件说明见[deploy/README](../deploy/README.md)，上线差距和优先级见[13](13-已知限制与后续路线.md)。
