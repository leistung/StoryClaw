# 08 任务、确认与积分计量

## 为什么有三种任务记录

| 对象 | 负责什么 |
| --- | --- |
| AgentRun / AgentEvent | 一次创作统筹请求、工具调用、状态和顺序事件 |
| WorkJob | 一项具体持久工作，如生成章纲、写章、索引、分析 |
| StudioTask | 跨步骤推进的有限计划，如连续写作或来源分析 |

Run可以提交Job，计划可以组织多个Job；它们不是三份独立模型循环。SQL记录状态，Worker领取执行。浏览器通过任务编号和事件序号续读，切换Tab不应重复发起请求。

## 提交与并发保护

请求编号绑定参数指纹；同编号不能换参数来复用结果。服务器检查用户、作品/章节范围、已有活动任务、方法版本和依赖条件。相同作品的冲突写操作受到限制，不能同时无序覆盖大纲与正文。

任务完成前会重验基础正文哈希和依赖。若作者已手动编辑，迟到结果应保留候选或报告冲突，不能盖掉新版。

### 多用户并发的实际含义

WorkJob消费者组成并发池，不同账号的任务可以同时调用同一模型和同一平台API Key，各自保存结果、预留积分并结算。某个账号已有运行任务时，领取器跳过它等待中的任务，继续领取其他账号的工作。一个任务异常不会结束其他消费者。

同一本书同时仅执行一个Job，是保护**作者自己**重复点击、多页面提交或多个写作步骤互相覆盖。它不是共同编辑权限；作品、章节和创作接口仍检查登录账号归属。前端隐藏按钮不能代替这些后端校验。

领取过程使用短事务级PostgreSQL咨询锁，先检查跨实例的账号/作品限额，再通过行锁认领；模型调用期间不持有这个全局咨询锁。执行者有独立租约和心跳，过期任务不自动重发付费请求；失效执行者不能开始新的计量预留、覆盖正文或激活知识索引。

每个Worker默认按CPU/内存估算本地槽数，也可显式配置；默认没有额外的集群总量上限，绝不存在固定“四个用户”的产品限制。多实例需要共享同一任务数据库，所有实例的全局和账号限额配置须一致。详见[02配置项](02-本地运行与配置.md)。

同一个Key可供平台内多个账号使用，但所有调用合计消耗供应商账户的并发、速率和余额。当前没有自动发现供应商额度或分布式按Key令牌桶；`WORKER_GLOBAL_JOB_CONCURRENCY`是可选的Job总量保护，不等同于每秒请求数限制。遇到上游限流不会靠无限重试制造更多付费调用。

Worker连接池允许每个执行槽的工作Session和独立计量连接同时工作，并为心跳留出余量，避免固定小连接池被长事务占满。生产必须按所有API/Worker副本合计规划PostgreSQL连接数，必要时采用连接池代理；增加Worker不等于数据库或模型容量同步增加。来源分析等StudioTask仍有各自消费者，不应把WorkJob并发池理解为所有后台工作都已自动伸缩。

### 社区共享与独立副本

产品边界是：原书仅作者可写；他人只读作者公开的内容；复制必须生成归复制者所有的新Book和全新的章节/设定标识，之后双方修改独立。允许同名，标题不承担数据身份。

**当前实现**的Publication是作者冻结的公开正文快照，尚未实现全部创作Tab共享及整书复制。后续扩展应由作者明确选择分享范围及是否允许复制，读者不能借公开阅读接口访问原书的私有API。复制作为不调用模型的后台任务，固定来源快照版本、支持重复提交幂等；不得复制账号资料、积分、任务、私有聊天或原书检索索引。新副本的确认与知识索引应重新建立。来源下架或快照版本变化时要明确失败，不能悄悄改读作者未发布的草稿。

## 哪些事情需要人工确认

开书资料、总纲、本章情节、已有正文覆盖、候选采用、正文入库、有限连续计划自动采用授权，以及冻结发布快照，都有相应确认路径。

助手的选项问题只是收集信息，不能替代发布/覆盖等授权。确认还绑定具体版本；确认完又改资料，需要重新核对，不能无限沿用旧确认。

连续计划默认停在章纲确认与正文审阅处。只有作者明确批准的有限范围和预算才允许自动采用，不是一句“继续”就永久授权全书发布。

## 暂停、取消与失败

暂停/取消阻止后续调用预留，已发出的供应商请求可能仍完成并产生成本。页面断开、HTTP超时或Worker进程退出，并不自动证明供应商未执行。

结果未知时不自动重复付费调用。先查看任务、用量、已保存候选和检查点，确认后显式恢复。失败候选不应自动进入正文、索引或发布快照。

## 积分怎样计算

1. 调用前按实际模型、输入/输出上界和当时价格预留。
2. 模型执行由AI包完成，平台提供预留与结算回调。
3. 按可获得的供应商token用量与原价格快照结算，并释放剩余预留。
4. 供应商用量未知或超出可结算范围时保留待核对状态，不能声称上游没有成本。

平台积分与智谱账户余额不同：用户平台积分足够，也可能因供应商额度不足失败；管理员加平台积分不能给上游充值。主统筹Run也计量，当前保留100积分上限；连续计划有自己的预算约束。

旧接口的汇总计费在实际逐调用计量生效时抑制，避免重复扣分。降级时两款模型分别记账，不把备用模型的调用记到主模型名下。

## 异常格式与运营对账

首页选题格式异常按现有政策补偿本轮用户积分，同时保留供应商用量。不能因为补偿用户就删除成本记录，也不能通过对账再次补扣已退款的格式失败调用。

中台支持人工登记供应商回执、原价格快照复算、幂等对账和可选余额调整；默认登记用量，不自动补扣。自动拉取供应商账单、完整财务结算仍未实现。

## 创作生成计划与执行记录

工作台的大纲和角色 / 世界观 / 情节设计按钮先创建 AgentRun，由 Agent 消费者拟订结构化生成计划，不立即提交正式 WorkJob。计划在右侧助手显示分卷或分组内容、目标数量、每项字数，以及按当前平台模型价格计算的 Token 和积分估算。估算不包含已发生的计划讨论、后续修改、正文生成和入库，也不是费用上限；实际按模型用量结算。

作者可通过 `POST /agent/runs/{id}/plan` 提交补充要求。该操作校验当前确认卡 ID，使旧确认卡失效，复用持久请求重新拟订计划。`POST /agent/runs/{id}/decisions` 确认后才提交正式任务。作品资料、大纲或设定变化会使计划快照失效；Worker 执行前也再次核对快照。计划生成、作者确认和正式产物的审阅采用是不同阶段。

连载大纲依据已确认卷数，分别生成总览和各卷详情；固定大纲进一步逐卷、每批最多五章展开。设计档案每批最多三张，校验计划数量、重复名称和描述详细程度。模型返回不足时明确报错，不把几句概述当作完整产物。连载仍保留可调整的未来方向，不预写全部章纲。

主 Agent 的工具调用以及关联 WorkJob 的校验、模型调用、写作 / 审阅节点、分卷 / 分批生成和保存步骤写入已有 AgentEvent 日志。页面分页重放事件，展示可折叠步骤、函数名、调用参数、有限长度的返回摘要、耗时和错误。记录不包含系统提示词、密钥或模型内部思考。助手回答使用 Markdown 渲染，支持表格、列表和代码，不执行原始 HTML。

## 工作台唯一 AI 入口：对话草稿与正文引用

工作台的 AI 快捷按钮只调用前端 `prepareJobPrompt` / `stageAssistantPrompt`：将可编辑需求放入右侧助手，不提交 AgentRun、WorkJob，也不调用模型。大纲、设定、章纲、正文、场景任务单、入库、语义检索、来源分析、连续计划创建与恢复均遵守这一规则。作者点击助手发送后，才以 `entry=chat` 创建请求，由 Agent 根据最终文字决定工具。手动编辑、保存、审阅采用、停止任务等作者操作保留原有功能。

输入框支持折叠的选区、光标和完整章节引用。选区显示章节与行范围，展开可看全文。引用包含目标章节、正文版本和按非空白 Unicode 字符计算的位置；编辑器快照仅留在本地草稿，发送前保存必要改动、核对快照并移除本地字段。草稿按账号和作品隔离；切换章节不会改变已绑定引用。输入失败或发送期间的新编辑不会被清空。

后端在接收新请求、调用模型前和执行工具前验证引用版本及所属章节。重复片段按绑定位置定位，不依赖字符串第一次匹配。润色和续写读取本章完整正文；续写还接收光标之后的正文和作者要求，返回可插入候选。作者采用时再次校验版本，保留未修改 HTML 格式、后文和旧稿快照。旧请求的幂等重放返回原记录，不会重复执行。

Agent 可通过 `setting.read` 查询真实设定 ID 与版本，使用 `setting.update` 提出修改候选；右侧展示修改前后，作者采用后才保存，原值保留在运行记录中，并使受影响的正文和章纲重新待核对。`skills.list` / `skills.read` 展示可用方法；执行日志包含实际加载的 Skill、工具参数、返回摘要、耗时和错误。连续或来源分析计划通过 `plans.create` / `plans.resume` 提议，实际执行范围、预算和自动采用权限仍由真实确认卡批准。
