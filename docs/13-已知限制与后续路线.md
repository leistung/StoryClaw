# 13 已知限制与后续路线

核对日期：2026-10-26。此处列的是当前边界和建议顺序，不是已实现功能承诺。

## 目前不能声称完成的事情

- 没有“自动写出可签约、可盈利、几百万字优质小说”的验收。模拟编排、合成拆章、模型连通性与真实文学质量是不同证据。
- 连续计划是有限范围和预算的工作流，不是无限自主写作；本章确认、作者审阅、来源基线和版本保护不能跳过。
- 结构化角色知情和引用范围已实现，但原文检索与生成仍需人工审阅，不能保证角色视角绝不泄漏或所有伏笔都自然回收。
- 旧稿接管和分支已实现来源、分析、索引、基线等机制，但没有对所有百万字稿件完成真实全量成本/质量/性能基准。
- 没有外部小说平台的官方自动投稿连接器、签约、作者收益分账或版权授权核验服务。
- `openai_responses`格式入口目前走Chat兼容路径，不能视为原生Responses能力已经完成，需单独补完和验收。
- 没有完整在线支付、退款及自动财务闭环；现有会员申请、人工开通和积分不等于支付系统完成。
- 当前Compose仍是开发模式，未交付生产高可用、灾备、完整告警或全部安全运营能力。
- WorkJob已支持多用户并发与多Worker协调，但没有千人真实生成压测、动态自动扩缩容或供应商按Key分布式速率限制，不能承诺1000个生成请求同时无等待完成。
- 社区当前公开正文快照；全部创作Tab只读分享、作者授权后独立复制整书属于明确设计边界，尚未实现。
- 管理端暂无独立自动化交互用例；近期检查包含类型/构建与服务冒烟，没有浏览器视觉全覆盖验收。

## 已知需要注意的技术问题

| 问题 | 现有保护 | 后续工作 |
| --- | --- | --- |
| API健康但AI初始化失败 | 启动日志记录警告 | 将存活与依赖就绪分开检查 |
| 超时/崩溃后上游结果未知 | 不盲目重复调用，保留候选、用量和任务 | 更完整的恢复演练与运营处理指引 |
| 模型参数与费用变化 | 模型适配、快照计量、预算和配额降级 | 持续兼容评估、供应商账单接入 |
| 改早期章节影响大量后文 | 指纹失效、复核提示与有效代次 | 更清晰的影响预览、人工批量复核体验 |
| 长篇检索与角色视角 | 章节范围过滤、有效索引、结构化规则 | 有人工评分的长程记忆与视角评估集 |
| 代码历史兼容入口较多 | 专业服务复用与架构边界测试 | 持续减少重复入口，保留明确迁移策略 |
| 开发库与迁移基线差异 | 已有Alembic文件和隔离测试 | 对真实数据副本做升级/回滚演练 |

## 建议推进顺序

**第一阶段：可控试运营。** 完成生产镜像/网关、密钥管理、备份恢复、监控和依赖就绪；限制并发与生成预算，用现有确认流程开展小范围内测。

**第二阶段：商业交易闭环。** 明确会员权益，接入真实支付/退款/回调幂等及财务核对；完善内容发布、投诉、审核和用户数据操作。

**第三阶段：长篇质量与规模。** 建立逐章滚动的真实评估样本，记录连贯性、角色知情、重复、字数、作者修改量、单章成本和恢复结果。先验证稳定章节，再扩展旧稿接管与长篇规模，而不是把百万字当作一次生成请求。

**第四阶段：按瓶颈拆分。** 依据压测拆数据库、对象存储、Worker或知识服务，完善发布回滚和容量规划。不能仅因目录拆成包就宣称系统可无限扩容。
