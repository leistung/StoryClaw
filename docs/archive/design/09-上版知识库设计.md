> 历史归档：保留当时方案或验证结果，不代表当前实现。现行说明从[阅读导航](../../00-阅读导航.md)开始；文中旧命令不应直接照做。

创作流程与包边界的主文档见 [NOVEL-WORKFLOW.md](08-上版小说工作流.md)。本文维护索引设计细节，区分当前实现和后续目标，避免把设计当成已完成的功能。

## 数据职责

| 存储 | 保存内容 | 数据地位 |
| --- | --- | --- |
| PostgreSQL | 用户、作品、卷、章节正文、手工角色/场景/物品设定、大纲、积分账本、平台配置、审计 | 业务事实来源 |
| Milvus | 从章节及设定生成的文本切片向量、检索所需来源标记 | 可重建的语义检索索引 |
| Neo4j | 人物/地点/物品/伏笔之间的关系、事实来源和时间范围 | 可重建的事实关联索引 |
| 对象存储 / 持久文件卷 | 封面、插图、附件、导出文件 | 文件原件，需独立备份 |

图片的资产 ID、所有者、作品 ID、文件键、类型、大小、哈希和生成来源保存在 PostgreSQL。
不把大图片的 Base64 塞进用户或章节表，也不把 Milvus 当图片文件仓库。当前仅有 cover_url，资产表和上传接口仍待实现。

## 当前能力

已有 PostgreSQL 业务模型、按 user/book 分隔的 Milvus collection、Neo4j 实体/关系和章节来源。
当前实体按名称合并，缺少完整别名与时序；向量切片缺少正式的正文版本与模型版本字段。
本批加入 Embedding 响应校验、图谱章节关系事务替换、正文变更后的 pending 标记和持久入库检查。
这些修正不等于已经解决所有上下文矛盾，特别是旧索引过滤和时间线仍需下述结构支持。

## 后续表与索引设计

PostgreSQL 增加：

- chapter_versions：不可变正文版本、parent_version_id、内容哈希、作者或生成任务、创建时间。
- knowledge_jobs：user_id、book_id、chapter_id、source_version_id、索引版本、queued/running/succeeded/failed、错误、尝试次数及租约。
- knowledge_manifests：当前生效的章节版本、切片版本、Embedding provider/model/dim、索引时间及两种索引状态。
- story_entities：稳定 entity_id、类型、规范名称、别名；人工设定和模型推断分开保存。
- story_facts：实体、属性或关系、值、来源章节与文本片段、故事时间、置信度、人工确认状态。
- consistency_findings：冲突类型、相关事实、章节定位、解释、待确认/已处理状态，不直接修改正文。

Milvus 每个向量关联 user_id、book_id、chapter_id、chapter_number、source_version_id、chunk_id、内容哈希、Embedding 模型标识及索引版本。
索引按 Embedding 模型和维度划分；所有查询必须强制过滤用户和书籍，并通过生效清单排除旧版本。
保留当前 collection 到新索引校验通过，再切换读路径；重建时先写新版本，不先删旧索引。

Neo4j 使用稳定 entity_id 合并节点，规范名称不作为唯一身份。
关系记录来源章节、正文版本、事实 ID、有效起止时间；相互矛盾的断言分别保留，不能用最新描述覆盖旧事实。
人物死亡、复活、道具转移等变化是时序事实，不简单判为矛盾。同名不同人物保持不同 ID。
手工确认的设定优先；模型推断不得自动覆盖作者确认的设定。

## 入库流程

保存正文版本 → 同事务写索引任务 → worker 获取固定版本 → 切片、向量化、提取事实 → 写新索引版本 → 验证数量与来源 → 切换生效清单。

任务重试以章节版本和索引版本作为幂等键。
PostgreSQL、Milvus、Neo4j 不做跨库分布式事务；清单控制可见性。任一写入失败保持旧生效版本，并记录错误供重试。
章节删除先撤销检索可见性，再异步清理索引；正文是可重建索引的依据。

## 写作时怎么用

1. 由后端确认作品所有权和当前目标章节。
2. 加载作者设定、大纲、最近章节与阶段摘要，形成基础上下文。
3. 根据写作计划生成检索问题，从 Milvus 找相关历史片段。
4. 识别相关实体，从 Neo4j 补充关系、事实和未回收伏笔。
5. 用当前正文版本和目标章节边界过滤，避免过期索引及未来剧情泄漏。
6. 对片段去重，按 Token 预算排序；每条证据带来源章节。
7. LangGraph 生成草稿，再执行人物属性、关系、时间线、地点、物品归属与伏笔检查。
8. 冲突生成可解释提示及证据，由作者确认修改；确认后保存新正文版本并重建索引。

不承诺向量检索本身保证一致性：Milvus 帮助找到相关内容，Neo4j 帮助核对关联事实，最终结合明确规则与作者确认。

## 验收案例

- 用户 A 不能通过检索得到用户 B 的人物和章节。
- 同一用户不同作品中相同人名互不影响。
- 重写章节后旧关系和旧向量不可继续参与检索。
- 更换 Embedding 模型时禁止混检，并能恢复重建任务。
- 写第 N 章时不泄漏 N 之后的正文及未来事实。
- 持久库中断、worker 重启、重复任务不会将缺失索引标成成功。
- 角色合理成长不被当作冲突；与已确认设定相矛盾时展示具体来源。

以上验收项中的隔离、时序、版本切换及任务恢复需要随后续实现逐项自动化验证。

## 2026-10-25 实现更新

已实现：正文确认哈希 → 持久 index 任务 → 入库前 pending → 持久两库成功且版本不变才 loaded；历史未入库时阻止下一章 AI 写作；检索故障不再静默回退；图谱按全章分段抽取而非只看前 4000 字；检索上下文附真实章号和来源 ID。自动设定同步已停用，AI 推断不会偷偷修改作者角色卡。

尚未实现：不可变索引版本 manifest、跨库原子切换、稳定实体 ID/别名与完整时序事实。当前依靠 SQL 的 pending/loaded 和章号边界阻止旧版/未来事实参与写作，不等价于完整版本化知识库。
