# 04 系统架构与运行原理

## 一次写作请求经过哪里

```mermaid
flowchart LR
    A[React作者端] --> G[FastAPI Gateway]
    B[React运营端] --> G
    G --> S[平台应用服务]
    S --> P[(PostgreSQL)]
    S --> Q[持久任务]
    Q --> W[独立Worker]
    W --> H[StoryClaw Harness]
    S --> H
    H --> M[外部文本与Embedding API]
    H --> V[(Milvus)]
    H --> N[(Neo4j)]
    S --> O[MinIO私有原稿]
```

浏览器只访问平台API，不持有供应商密钥，也不直接连接数据库。AI包由API/Worker的Python进程导入，不是另一个HTTP微服务。

## 为什么后端里有app和packages

`app`回答：谁能操作、如何读写SQL、怎样排队、需要谁确认、积分如何结算。`packages/harness/storyclaw`回答：怎样理解创作要求、选择能力、组织提示、执行Graph、生成内容和检索证据。

依赖方向为`app → storyclaw`。AI包通过Ports和注入回调使用平台能力，不能反向导入`app`、FastAPI或SQLAlchemy。平台也不直接调用LangChain的`ainvoke/astream`；模型推理在AI包中完成。这些边界由自动测试检查。

例子：AI提出“读取上一章”，调用工具；平台适配器先检查用户、作品与章节范围，再读取资料返回。AI不能通过一句提示绕过权限。

## 业务模块如何连接

```mermaid
flowchart TD
    Pages[前端 pages 路由与页面组合] --> Features[features 各业务模块]
    Features --> HTTP[lib/http 认证与传输]
    Features --> Draft[assistant 草稿与正文引用]
    Draft --> Chat[右侧助手：作者编辑并发送]
    Chat --> HTTP
    HTTP --> Routes[gateway HTTP 路由]
    Routes --> Services[services 应用服务]
    Services --> Ports[adapters/storyclaw 公共授权与事件]
    Ports --> Registry[capabilities 显式能力路由]
    Registry --> Query[资料与查询]
    Registry --> Creative[规划与创作候选]
    Registry --> Jobs[持久化后台任务]
    Creative --> Harness[storyclaw AI 工作流与 Skill]
    Jobs --> Worker[Worker 执行器]
    Worker --> Harness
    Services --> SQL[(SQL：版本、事件、任务与积分)]
```

`schemas` 按领域定义请求和响应，维持统一公共导入入口。候选采用事务归 `services/agent`，连续计划控制归 `services/jobs`；两者可由 HTTP 和助手共同调用，业务服务不再反向调用 HTTP 路由。Ports 每次执行都重新检查归属、取消状态和引用版本，再交给对应能力模块。

## API和Worker为什么分开

API接收HTTP请求并返回数据、事件或任务编号。Worker执行持久化队列，负责需要较长时间的生成、来源处理、索引、发布与清理。它们安装相同代码，角色不同。

页面切换后，从SQL任务和事件恢复状态，不应重新提交同一个付费请求。不是每个API都排队：只读状态及部分短操作可以直接执行；长创作操作以任务为主。

一个Worker进程可以运行多个异步Job消费者，多个Worker实例也能共享SQL队列。账号和作品的执行限额在SQL领取时统一校验，因此不会因多开一个实例就重复领取同一任务。当前本地Compose支持扩展Worker副本，但跨服务器部署、数据库连接容量和供应商限流仍须单独规划；详见[08任务与计量](08-任务确认与积分计量.md)。

## 启动时做什么

`app.main:app`转出`app.gateway.app`的ASGI应用。lifespan创建开发期缺失表、加载数据库平台配置、构建检查点并注入模型/上下文/工具回调。

Compose将API的`WORKERS_ENABLED`关闭，独立Worker显式开启消费者，并写心跳健康文件。数据库仍是任务事实源，不靠浏览器内存或页面Tab保存执行状态。

目前启动时AI依赖初始化失败会记录警告，基础API仍可能启动。因此`/health`成功不能代替真实创作检查。这是当前需要继续改进的就绪检查边界。

## 容器和数据

Docker容器是同一台主机上隔离的进程环境，不是每个容器各有一台完整虚拟机。Linux服务器运行Docker；macOS开发时通常由Docker Desktop的Linux虚拟机承载。

容器内部可以都使用8000，只要宿主机发布端口不冲突。内部服务名用于容器间通信。数据库卷在容器之外持久化；删除或重建容器不等于删除卷。

容器拆分有利于升级和职责隔离，但同机部署仍共享CPU、内存、磁盘和故障域，不等于高可用。
